## 1. The 288-case structured benchmark (`testing/test_algorithm.py`)

**This is the only benchmark in the paper that actually exists and runs.** I ran it live on the current code (288 cases, with the cough-clarification override applied, exactly as the paper's Table 8 describes).

**Reproduced result:**
```
total_tests: 288
exact_matches: 283   (98.3%)
partial_matches: 0
failed_detections: 5
false_positives: 0   ← see "misleading metric" below
```

### The paper says 288/288. The code says 283/288.
There is no configuration of the current code + data that yields 288/288. The deployed hybrid pipeline scores 283/288 with clarification; the dictionary-only path scores 286/288. The "100% / all 288 achieve exact match" statement in the Table 8 discussion is **not supported by the artifact.**

### The 5 failures (the paper claims there are none):
| # | Input | Expected | Detected | Type |
|---|-------|----------|----------|------|
| 207 | `hindi masakit ang katawan ko` ("I do NOT have body pain") | NONE | BODY_ACHES | **Genuine false positive** (negation miss, no safety net) |
| 212 | `ang ubod ng init ngayon` (idiom, "peak of the heat") | NONE | FEVER | **Genuine false positive** (false-positive trap) |
| 222 | `walang sore throat` ("no sore throat") | NONE | BODY_ACHES | **Genuine false positive** (spurious, unrelated label) |
| 275 | `nagsusuka ng dugo` ("vomiting blood") | NONE | STOMACH_ACHE | Label mismatch — **but red-flag layer catches it** ✔ |
| 282 | `swollen throat` | NONE | SORE_THROAT | Label mismatch — **but red-flag layer catches it** ✔ |

**Fairness note (important for your defense):** I verified that cases #275 and #282 *are* caught by the separate `detect_red_flags()` layer (`blood_vomit` and `severe_allergic_reaction` fire), so in the real consultation flow the recommendation would be suppressed and the user referred. Those two are not safety failures — they're label mismatches in a detection-only benchmark.

**But #207, #212, #222 are real bugs with no safety net:** the system tells someone who said *"I do not have body pain"* that they have BODY_ACHES, and would recommend body-pain medicine. That directly contradicts the paper's sentence *"the system never detected a wrong symptom."* It did, three times, on its own benchmark.

### The "false_positives: 0" metric is misleading.
The harness reports `false_positives: 0`, but the 5 failures above are literally false detections on NONE-expected adversarial inputs. The counter only tallies FPs that co-occur with a correct detection, so it structurally cannot count these. **Do not cite "zero false positives" — it's an artifact of how the metric is defined, not a real property.**

### The raw (no-clarification) number checks out.
Reproduced raw: **~80.6% exact, micro-F1 0.850** (dictionary) / 79.5%, 0.846 (hybrid). The paper's 81.2% / 0.852 is within normal drift. This number is fine to report.

## 2. The 9-case stress set and 80-case real-user simulation — **do not exist**

The paper reports "9/9 exact matches on the semantic stress set" and "72/80 (90%) on the real-user simulation," and builds the **"377 total cases, zero failures"** headline on them.

I searched the entire repo (excluding venvs and the `_For-Mendo/` archive) for these datasets and any code that runs them. **They are not there.** The only files that mention "stress / real-user / simulation / figurative" are `generate_methodology_docx.py` and `generate_duration_updates_docx.py` — i.e., the scripts that *write those claims into the thesis*, not scripts that *evaluate* anything. There is no 9-row or 80-row dataset; the only small data files are a 2-row template and a 15-row sample.

**Consequence:** the "377 total cases / zero outright failures" claim is unverifiable and, given §1, almost certainly wrong (the one set that exists has 5 failures). If a panelist asks to see the 9-case and 80-case results, **there is currently nothing to show.** This is the single most exposed claim in the evaluation section.

## 3. Table 10 (vs XLM-RoBERTa, mBERT, SVM, LogReg, RandomForest) — **no code, not reproducible**

The Methods chapter describes a careful comparison: 5-fold stratified cross-validation, transformers fine-tuned 10 epochs with AdamW (lr 5e-5), TF-IDF baselines, etc. I searched for the code that produces it:

- No `StratifiedKFold`, `cross_val`, `n_splits`, `AdamW`, `xlm-roberta`, `bert-base-multilingual`, `OneVsRest`, `LinearSVC`, or `RandomForest` anywhere in the repo (outside library venvs).

**That table cannot be reproduced from this repository.** Whatever produced it (a separate notebook/Colab?) is not committed. For a thesis, that's a reproducibility gap a technical panelist can press on — keep the script that generated Table 10 and commit it.

### What the repo *does* contain instead: `experiments/retrieval_benchmark/`
This is a **different** comparison than Table 10 — it benchmarks embedding-**retrieval** models (TF-IDF, MiniLM, Qwen3-0.6B, BGE-M3, Jina-v3), not fine-tuned classifiers. I aggregated all 21 saved runs (same 288-case CSV):

| Model | with clarification | raw |
|---|---|---|
| **dictionary** (Mendo Stage 1) | **99.3%** (286/288), F1 0.997 | 80.6%, F1 0.850 |
| **current_hybrid** (deployed pipeline) | **98.3%** (283/288), F1 0.993 | 79.5%, F1 0.846 |
| tfidf_char | 53.5% | 40.6% |
| tfidf_word | 46.9% | 36.5% |
| bge_m3 | 46.5% | — |
| qwen3_0.6b | 42.4% | — |
| jina_v3 | 34.0% | — |

**Two findings that matter:**
1. **The dictionary alone (99.3%) beats the full hybrid (98.3%).** The semantic layer *adds* the 3 false positives from §1 and nets **negative** on this benchmark. This is concrete evidence for what the honest review already argued: the "hybrid AI" semantic stage is not pulling its weight here. (It may still help on inputs outside the dictionary — but this benchmark doesn't show a benefit.)
2. The big embedding models underperform badly (34–46%), which *supports* the paper's general thesis that small/rule-based wins on this narrow task — but with **different models and numbers than Table 10 reports.** Use these real numbers, or re-run and commit Table 10's actual code.

## 5. Recommendations (to make the evaluation honest and defensible)

**Must do before defense:**
1. **Change "288/288 (100%)" to the real "283/288 (98.3%)"** everywhere, and describe the 5 failures honestly (note that 2 are caught by the red-flag layer, 3 are true negation/false-positive misses on the roadmap to fix).

3. **Stop citing "zero false positives"** — it's a metric artifact; the system has demonstrable false positives.
4. **Commit the Table 10 generation script** (the CV/transformer comparison). If it can't be recovered, either re-run it and commit it, or replace Table 10 with the real `retrieval_benchmark` numbers (§3) and relabel it as an embedding-retrieval comparison.
5. **Explicitly label the 288 set as "LLM-generated synthetic benchmark"** in the methodology, as the panel demanded.

**Should do (strengthens the work):**
6. Fix the 3 negation/false-positive bugs (#207, #212, #222) — they're concrete, small, and fixing them lets you honestly raise the score.
7. Acknowledge that the dictionary alone matches/beats the hybrid on this benchmark, and frame the semantic layer's value as *out-of-dictionary recall* (and then show an example where it actually helps — otherwise the panel will ask why it's there).
8. Get even a small **externally-annotated** test set (your Iteration 2 pharmacist) — one independent eval is worth more than 377 self-authored cases.
